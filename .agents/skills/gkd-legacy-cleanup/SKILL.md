# GKD Legacy Cleanup

这是临时、按需调用的清理 Skill，不进入 `gkd-main` 默认路由，也不提供兼容模式。只有 main 明确给出一个老项目根目录、清理目标和删除授权时才可使用；本 Skill 完成后可按用户指示删除。

## 边界与授权

- 只在指定老项目根目录内工作，不触碰生产 `~/.codex`、其他项目、当前 GKD 仓库自身的 `.gkd/` 活动记录或无关普通业务文件。
- `.gkd/archive/` 中的历史 Markdown 默认是事实记录并保留；其中若含可执行入口，或用户明确要求彻底删除，才可列入待清理项，并在报告中区分活动机制和历史记录。
- “活动引用”仅指活动文件中仍可解析（路径、命令或链接目标存在）且明确指向已确认旧 GKD 机制的引用；仅有关键词、历史描述或无法确认归属的文本不属于活动引用。活动文档中指向这些已确认旧机制、但目标已不存在的失效链接，可与活动引用一起列入待授权清理项；历史归档中的事实引用仍保留。
- 不恢复旧状态机、合同、watcher、bundle 或迁移入口，不把删除动作扩展为重构或兼容层设计。
- 任何删除必须逐项得到 main/用户的明确授权；材料不清、路径共享、证据不足或发现仍被普通业务使用时停止，不猜测、不静默删除。

## 第一阶段：只读盘点

先对目标项目做只读清单，不修改文件或 Git。检查项目内：

- `.agents/skills/`、`.codex/agents/` 中的旧 GKD Skill、角色和提示词；
- `scripts/`、hooks、配置、CI/workflow、README/AGENTS/文档/模板中的旧入口和引用；
- 任务状态、合同、队列、日志、receipt、offer、claim、activation、journal、旧 automatic route、fixed-head、watcher、bundle/manifest/lock 等标记及其调用关系。

对每个活动引用解析目标并记录目标是否存在；把仍指向已确认旧机制的可解析引用和对应失效链接分别列出，均不得绕过授权直接删除。

每项记录路径、符号或引用行、是否可执行、直接调用方和证据。按以下四类输出：

1. 当前有效规则：仍被当前项目工作流使用，必须保留；
2. 明确遗留：确认属于旧版 GKD 活动机制，可申请删除；
3. 普通业务内容：与 GKD 无关，即使命中关键词也保留；
4. 证据不足：无法确认归属、调用关系或是否为历史事实，停止并交回 main。

先把盘点报告交给 main，未经确认不得进入删除阶段。

## 第二阶段：按授权清理

收到逐项授权后，仅删除已确认的旧 GKD 可执行入口、角色/Skill、状态文件、脚本、仍指向这些机制的可解析活动引用和对应失效链接；同步清理因此变为空的目录和明确失效的文档链接。不要删除普通业务代码、用户数据或默认保留的历史归档，不迁移旧状态，不新增替代入口。

完成后做文件存在性检查、引用扫描、`git diff --check` 和目标项目适用规则检查。仍有歧义或删除条件不满足时保留现场并报告阻塞；不要用宽泛的关键词扫描结果替代逐项判断。

## 报告格式

报告列出盘点分类、已授权删除项、保留的当前规则/普通业务/历史记录、失效引用处理、验证命令与结果、未决证据缺口和后续建议。不得记录生产用户目录、令牌、账号或其他敏感值。清理 Skill 本身及其文档引用的删除时机留给用户另行授权。
